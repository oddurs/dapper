# Config-object incumbents (ECharts, Highcharts, Chart.js, Plotly)

## The vision (what this tradition believes a chart is)

A chart is a **product feature**, not a sentence in a visual language. It is a named, recognised
artifact — "a stacked bar chart" — whose entire visible surface is addressable by name: title,
legend, tooltip, zoom slider, export button, animation, annotation, screen-reader description.
The library owns the pixels and the interaction; the user owns the settings.

The corollary is that the authoring artifact is **a serialisable document, not a program**. Because
the spec is a plain tree, it can be written by a non-programmer, stored in a database, generated by
a backend, diffed in review, versioned, themed, and shipped across language boundaries. Plotly makes
this literal: one machine-readable `plot-schema.json` generates the Python, R, and Julia APIs.
Highcharts' own docs justify object literals as giving "a clean, human readable and low space
consuming config object."

The ECharts paper states the goals plainly: "easy-to-use, rich built-in interactions, and high
performance." Note the middle one. Interaction is a *founding* goal here, whereas grammar-of-graphics
tools bolted selections on years later. That difference explains most of the market share.

## Core abstraction

**The `option` tree: a deeply-mergeable partial record.** Rendering is
`interpret(merge(library_defaults, theme, per_type_defaults, user_options))`. Highcharts layers this
explicitly — `Highcharts.setOptions()` globally, `plotOptions.<type>` per series type, then the
`series[]` entry. Plotly formalises the tree: a root with `data` (array of typed *traces*), `layout`,
and `frames`, where every attribute has a dotted path — `layout.annotations[].text`,
`data[type=scatter].name`.

The load-bearing consequence: **every field is optional**, so the type of a spec is
`DeepPartial<Everything>`. Validation is therefore necessarily a runtime walk over a schema.
Plotly's shipped `dist/plot-schema.json` is **4.4 MB, 49 trace types, ~11,340 leaf attributes**
(measured, current master). That is the grammar — it just isn't checked by a compiler. Vega-Lite's
JSON-Schema problem is not a grammar problem; it is a config-tree problem, and Vega-Lite inherited it.

ECharts alone crept toward encoding with `dataset` + `series.encode`, motivated by "(I) Provide the
data, (II) Mapping from data to visual to become a chart" and by data reuse across series:

```js
dataset: { source: [['product','2015','2016'], ['Matcha',43,85], ...] },
series: [{ type: 'bar', encode: { x: 'product', y: '2015' } }]
```

This is channel encoding grafted onto a config tree, and it remains optional and second-class.

## Unique contributions

1. **A completeness checklist nobody else ships.** Tooltips (axis/item trigger, shared, formatter),
   legends (toggle, scroll, pagination), `markLine`/`markArea`/`markPoint` and Plotly shapes/annotations,
   `dataZoom` (slider + inside-drag), `brush`, `toolbox` (save image, data view, restore),
   server-side and offline export, themes-as-data, enter/update/`universalTransition` animations,
   Highcharts `responsive.rules` breakpoints, locale packs. Grammar libraries typically ship 3 of these.
2. **Accessibility as a shipped module.** Highcharts' accessibility module targets WCAG 2.2 with a
   published conformance report, keyboard navigation, screen-reader regions, voice input, and
   sonification. This is *only possible because the chart type is known*: a library that knows "this
   is a bar chart with three series over Month" can narrate it; a library that only knows "rect marks"
   cannot. Closed typology is an accessibility asset.
3. **Large-data handling as a config flag.** Highcharts `boost` (WebGL, 500k points), ECharts
   `large: true` / `largeThreshold` / `progressive` / `progressiveThreshold` / `sampling: 'lttb'`,
   Chart.js `decimation`. The user flips a switch; they do not author a downsampling transform.
4. **Escape hatches that keep the ecosystem.** ECharts `custom` series: "there are countless chart
   types… custom series provides an approach for developers to create new chart types" — you return
   graphic elements from `renderItem(params, api)` and still inherit coordinate systems, animation,
   tooltips, and events. Chart.js adds plugin lifecycle hooks and *scriptable options* (any leaf may
   be a function of context). This is how a closed typology survives novelty.
5. **A solved SSR/hydration story, directly relevant to dapper.** ECharts:
   `echarts.init(null, null, { renderer: 'svg', ssr: true })` → `renderToSVGString()`, plus a ~4 KB
   client that `hydrate()`s legend toggles and highlight without loading the full library.

## Where it struggles

- **No composition algebra.** You cannot write `overlay(bar, line)` or `facet(by: region)`. You write
  a flat `series[]` array and hand-wire `xAxisIndex`, `yAxisIndex`, `gridIndex`. Small multiples are
  either N charts or manual `grid` coordinates. Plotly's `make_subplots` is a code generator, not an
  algebra. Reference-by-integer-index is the model's ugliest wart and a permanent source of dangling refs.
- **Expressive power is capped by an if-ladder.** Anything not in the typology requires dropping to
  `renderItem` or a plugin. There is no middle rung between "configure a bar chart" and "draw pixels."
- **Type safety is structurally impossible here.** Merge semantics force everything optional, so no
  static type can say "`smooth` is legal on line but not bar", "`stack` requires a shared axis", or
  "`xAxisIndex: 2` must reference an existing axis." ECharts had to invent
  `ComposeOption<BarSeriesOption | GridComponentOption | …>` to get a stricter type — and it only
  checks that used components are registered, never cross-field coherence.
- **Naming entropy is permanent.** Chart.js's own v3 tracker repeats "Rationalize option names," yet
  they refused to remove `data` from the config because "every chart would need to be updated and all
  StackOverflow answers would be outdated." When the API *is* the data format, nothing can ever be renamed.
- **Deep merge is a semantic trap.** Arrays merge by index; `null` and `undefined` differ; themes
  override silently; `setOption(opt)` merges while `setOption(opt, true)` replaces. None of this is
  expressible in a signature.
- **The layer above keeps getting rebuilt.** Plotly Express exists — "a wrapper for Plotly.py that
  exposes a simple syntax for complex charts" — which is an admission that the config tree is an
  assembly language, not an authoring language.

## Implications for dapper

- **Steal the checklist, not the shape.** Reserve typed slots in the v0.1 `Chart` for title, legend,
  tooltip, and annotation even if unimplemented. Retrofitting these into a pure grammar is exactly
  what went badly for the grammar lineage.
- **Replace deep-merge-of-partials with opaque records + total transformers.** Gleam has no optional
  record fields, no HKTs, and no `DeepPartial`. Lean on that: one fully-populated defaults record,
  mutated by `fn(Chart) -> Chart` builders (`chart |> dapper.legend(legend.right())`). Theming is an
  explicit `apply_theme(theme, chart)`, never global mutation. Keep `Chart` opaque from day one —
  in Gleam, adding a public record field is a breaking change, and this tradition proves the config
  surface grows forever.
- **Encode with ADTs the constraints Plotly validates with 4.4 MB of JSON.** Prefer one constructor
  per legal combination over generic parameters (no HKTs to lean on):
  ```gleam
  pub type Mark {
    Bar(category: Channel(Band), value: Channel(Continuous), color: Option(Channel(Discrete)))
    Line(x: Channel(Continuous), y: Channel(Continuous), color: Option(Channel(Discrete)))
  }
  ```
  A `Bar` that structurally *requires* a band channel and a continuous channel is the wedge: that
  check is a JSON-Schema pass in Vega-Lite and a runtime warning in ECharts.
- **Never use indices as references.** Where ECharts writes `yAxisIndex: 1`, dapper should hold the
  scale as a value inside the layer. This kills an entire bug class the incumbents live with.
- **Ship an escape hatch in v0.1, not v0.5.** A `Custom(fn(Datum, Coords) -> List(Element))` mark
  plus a raw-SVG annotation layer, designed so it still inherits axes, legend, and layout. Without it,
  the closed typology becomes a ceiling and users leave for D3.
- **Copy ECharts' SSR split literally.** Render to an SVG string on the BEAM; hydrate a small Lustre
  component for legend toggles and tooltips. Decide *now* whether the spec is `gleam/json`-serialisable
  — that property is what buys the config tradition its "generate on server, tweak in a DB, render
  anywhere" superpower, and it constrains whether `Custom(fn(...))` marks can live in the same type.
- **Don't chase option parity.** Fifteen production affordances done properly plus compiler-checked
  composition beats 11,340 attributes you cannot maintain.
